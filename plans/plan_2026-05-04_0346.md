## dbt Fusion Compatibility Plan for `dbt_dataengineers_materializations`

### Context

**Codebase:** 15 custom materializations, ~70+ macro files, all Snowflake-only (`adapter='snowflake'`). Package version 0.2.13, requires `>=1.3.0, <2.0.0`.

**dbt Fusion Engine:** Rust-based rewrite of dbt Core (currently in beta, GA targeting late 2025). Fusion has a re-implemented Jinja engine (`dbt-jinja`) and enforces stricter rules than Core. Custom materializations are on the roadmap but not fully supported yet — there is a known issue (#1568) where `{% if execute %}` inside custom materializations causes malformed SQL because Fusion renders with `execute=False` during static analysis.

**Key Fusion compatibility risks identified in this codebase:**

| Risk | Severity | Files Affected |
|---|---|---|
| `require-dbt-version: <2.0.0` blocks Fusion (v2.x) | **Critical** | `dbt_project.yml` |
| `run_query()` outside `{% if execute %}` guards | **High** | `immutable_table.sql`, `alter_column_comment.sql`, `alter_relation_comment.sql`, `external_access_integration.sql` |
| `builtins.ref()` — undocumented, may not exist in Fusion | **High** | `external_access_integration.sql` |
| `py_current_timestring()` — Python-specific, won't exist in Fusion | **High** | `snowflake__get_source_build_plan.sql` |
| `hooks` implicit variable in materializations — may not be available in Fusion | **Medium** | `stored_procedure.sql`, `user_defined_function.sql` |
| `flags.PRINTER_WIDTH` — may not exist in Fusion | **Medium** | `stage_file_formats.sql`, `stage_stages.sql` |
| `adapter.commit()` in 12 materializations — Fusion may handle transactions differently | **Medium** | All materializations except `immutable_table` and `materialized_view` |
| `graph.nodes` / `graph.sources` access in on-run-start/end hooks | **Medium** | 6 hook macros |
| `run_hooks(pre_hooks, inside_transaction=True/False)` — transaction-scoped hooks may behave differently | **Low-Medium** | 12 materializations |
| `load_result()` / `store_result()` pattern | **Low-Medium** | 5 files |
| `result.columns[0].values()[0]` on `run_query` results — agate Table API may differ | **Low** | 4 files |

### Implementation Steps

#### Step 1: Update `dbt_project.yml` version constraint

Change `require-dbt-version` to allow Fusion (2.x) while maintaining Core backwards compatibility:

```yaml
# Before
require-dbt-version: [">=1.3.0", "<2.0.0"]

# After
require-dbt-version: [">=1.3.0", "<3.0.0"]
```

This is the single most important change — without it, Fusion won't even load the package.

#### Step 2: Guard all `run_query()` calls with `{% if execute %}`

Fusion's static analysis renders macros with `execute=False`. Any `run_query()` that runs unconditionally will either fail or produce empty/malformed results.

**Files to change:**
- `macros/immutable_tables/snowflake/immutable_table.sql` — `check_if_transient()` macro uses `run_query` without guard
- `macros/adapters/snowflake__alter_column_comment.sql` — `run_query` on line 8 in an else branch, not execute-guarded
- `macros/adapters/snowflake__alter_relation_comment.sql` — same pattern
- `macros/external_access_integration/snowflake__external_access_integration.sql` — `run_query("select current_role()")` on line 22
- `macros/source_tables/helpers/is_csv.sql` — `statement('get_file_format')` + `load_result` pattern

**Pattern to apply:**
```jinja
{% if execute %}
    {% set result = run_query(my_query) %}
    {% set value = result.columns[0].values()[0] %}
{% else %}
    {% set value = none %}
{% endif %}
```

For each call site, add a safe fallback value when `execute=False` and ensure downstream logic handles the `none` case.

#### Step 3: Replace `builtins.ref()` with standard `ref()`

In `macros/external_access_integration/snowflake__external_access_integration.sql`, three calls use `builtins.ref()`. This is an undocumented internal Python API that won't exist in Fusion's Rust Jinja engine.

Replace:
```jinja
{% do authentication_secrets.append(builtins.ref(seret_name).include(database=true)) %}
```
With:
```jinja
{% do authentication_secrets.append(ref(seret_name).include(database=true)) %}
```

Apply to all three occurrences (lines 29, 32, 35). This is backwards compatible with Core.

#### Step 4: Replace `py_current_timestring()` with a Jinja-native alternative

In `macros/source_tables/snowflake/snowflake__get_source_build_plan.sql` line 35, `py_current_timestring()` is a Python-specific function from dbt Core's context that won't exist in Fusion.

Replace with `modules.datetime.datetime.now().strftime('%Y%m%d%H%M%S')` which uses dbt's Jinja `modules` context (available in both Core and Fusion):
```jinja
{%- set backup_suffix_dt = modules.datetime.datetime.now().strftime('%Y%m%d%H%M%S') -%}
```

#### Step 5: Remove `flags.PRINTER_WIDTH` usage

In `stage_file_formats.sql` (line 36) and `stage_stages.sql` (line 34), `flags.PRINTER_WIDTH` is read but the `width` variable is never actually used. Remove the dead code:
```jinja
{# Remove: {% set width = flags.PRINTER_WIDTH %} #}
```

#### Step 6: Guard `hooks` implicit variable access

In `stored_procedures/snowflake__stored_procedure.sql` (line 18) and `user_defined_functions/snowflake__user_defined_function.sql` (line 49), the `hooks` implicit variable is used:
```jinja
{%- set has_transactional_hooks = (hooks | selectattr('transaction', 'equalto', True) | list | length) > 0 %}
```

Fusion may not expose this variable. Guard it:
```jinja
{%- set has_transactional_hooks = (hooks | selectattr('transaction', 'equalto', True) | list | length) > 0 if hooks is defined else false %}
```

Note: `has_transactional_hooks` is set but never referenced in either file. Consider removing it entirely as dead code instead.

#### Step 7: Add `{% if execute %}` guards to `graph` access in hook macros

The on-run-start/end hooks access `graph.nodes` and `graph.sources`. While these already have partial guards (`flags.WHICH == 'run'`), Fusion's static analysis phase may still evaluate these. Add explicit `execute` guards as the outermost condition:

**Files:**
- `macros/tasks/enable_tasks.sql`
- `macros/alerts/enable_alerts.sql`
- `macros/monitorial/enable_monitorial_monitors.sql`
- `macros/file_formats/stage_file_formats.sql`
- `macros/stages/stage_stages.sql`
- `macros/source_tables/stage_table_sources.sql` (already has `{% if execute %}` — no change needed)

**Pattern:**
```jinja
{% macro enable_tasks() %}
    {% if execute %}
        {% if flags.WHICH == 'run' %}
            ...existing logic...
        {% endif %}
    {% endif %}
{% endmacro %}
```

This is backwards compatible — `execute` is `True` during runtime in Core.

#### Step 8: Make `run_hooks` calls resilient for Fusion transaction handling

Fusion may handle transactions differently from Core (DDL on Snowflake is auto-committed). The current pattern of:
```jinja
{{ run_hooks(pre_hooks, inside_transaction=False) }}
{{ run_hooks(pre_hooks, inside_transaction=True) }}
...
{{ run_hooks(post_hooks, inside_transaction=True) }}
{{ adapter.commit() }}
{{ run_hooks(post_hooks, inside_transaction=False) }}
```

This is the standard dbt Core materialization pattern. **Do not change this yet** — Fusion aims for compatibility with standard materialization patterns. If Fusion breaks on this, it's a Fusion bug they'll fix. Document this as a known risk area but don't alter the pattern.

#### Step 9: Add defensive `none` checks on `run_query` result column access

Wherever the pattern `result.columns[0].values()[0]` is used, add a defensive check:

```jinja
{%- set relation_type = relation_result.columns[0].values()[0] if relation_result and relation_result | length > 0 else 'table' -%}
```

This prevents crashes if Fusion's Agate-equivalent returns different structures.

#### Step 10: Add `flags.WHICH` guard to `stage_table_sources` `build` command

Currently `stage_table_sources.sql` guards with `flags.WHICH == 'run'`. Fusion also uses `build` as a valid command. For consistency and to support `dbt build`:

```jinja
{% if flags.WHICH in ['run', 'build'] %}
```

Apply the same to `stage_file_formats.sql` and `stage_stages.sql` which check `flags.WHICH == 'run' or flags.WHICH == 'run-operation'`:
```jinja
{% if flags.WHICH in ['run', 'build', 'run-operation'] %}
```

This is backwards compatible with Core (which also supports `build`).

#### Step 11 (Optional): Add package-level documentation

Add a note to the README about Fusion compatibility status and any known limitations (custom materializations are not yet fully supported in Fusion beta).
